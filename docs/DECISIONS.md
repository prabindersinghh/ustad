# Decisions

Why Ustad is built the way it is. Read before changing something that looks
odd: it may be deliberate. New non-obvious choices get a new entry at the
bottom (next id), never an edit that hides the old reasoning. When a decision
is reversed, mark it **Superseded by D-0xx**.

| Id | Date | Decision | Why |
|---|---|---|---|
| D-001 | 11-01 | **Phone PWA, not a native app** | No Xcode, no provisioning, no App Store review. The phone exposes what glasses do (POV camera, mic, speaker), so the client is a thin media source behind one interface. Meta glasses need the native Wearables Device Access Toolkit (iOS/Android, developer preview), which is a later swap of that layer. |
| D-002 | 11-01 | **Tool calls, not free-text verdicts** | `verify_step`, `flag_error` and `request_better_view` are auditable and executable. That is what makes the loop agentic, not a prompt that returns an opinion. |
| D-003 | 11-01 | **Boxes plus confidence from SAM, not masks** | Masks cost a decoder and add nothing to verification. A box and a score tell the reasoner where the part is. |
| D-004 | 11-01 | **The capture self-check grounds every target phrase on the expert's own keyframe** | A procedure ships only with phrases the perception model can find in that machine's own footage, under that light and from that angle. That is what makes later verification trustworthy. |
| D-005 | 11-01 | **Pluggable reasoning backend (hosted or Muse Glimmer)** | A factory's first question is whether footage leaves the site. Both backends speak the OpenAI protocol, so the swap is a base URL. Every step event records which backend judged it. |
| D-006 | 11-02 | **Batch ASR replaced by realtime ASR** (supersedes the README's original "batch ASR" row) | Live captions and voice commands need partials. Batch stays as the fallback for capture. |
| D-007 | 11-02 | **No Spark audio fallback** | Spark 1.3 doesn't take audio; the 1.2 path returned errors. Batch ASR is the only fallback. |
| D-008 | 11-02 | **Model calls run in `asyncio.to_thread`** | Blocking SDK calls froze the event loop and dropped WebSockets on the phone. |
| D-009 | 11-02 | **Live watching at about 1 fps, 2 SAM calls in flight, phone-side change gating** | A SAM round trip is about 2 s. Two in flight roughly double how often the box moves. Not sending unchanged views (a `still` heartbeat instead) makes a camera resting on the bench nearly free. |
| D-010 | 11-02 | **Auto-advance needs two confident passes on a newer, or held-still, view** | One pass on one frame is a guess. Two agreeing looks cut false advances without making the worker wait for a tap. |
| D-011 | 11-02 | **Reasoning effort: `low` for explicit checks, `minimal` for background looks** | Measured on fixed frames: default about 3.95 s, low about 2.4 s, minimal about 1.8 s, all 6/6 correct. Background looks are confirmed twice anyway. |
| D-012 | 11-02 | **Voice "done" fires on a stable partial (0.45 s), not on end of speech** | Waiting for end of utterance took about 3 s. Utterances over 6 words, or containing "not", are ignored ("I'm not done"). |
| D-013 | 11-02 | **Metered spend and a budget guard in the product** | Hackathon credit is finite ($150, working cap $50). Live watching is the expensive part, so it switches off at 95% and the job continues with tap and voice checks. |
| D-014 | 11-02 | **Safety gate: the model can never skip a worker past lockout, reading, timed or confirm steps** | Found in a security review. Jump-ahead is useful for visual steps whose end state proves them. For safety steps, "it looks done" is not evidence. `completed_through` is advisory and `inferable()` decides. Worker speech is quoted as data, never instructions. |
| D-015 | 11-02 | **Step kinds: visual, reading, timed, confirm** | Real machines need gauge readings in range (checked on the server, not trusted from the model), dwell times and operator confirmations that a camera can't see (e.g. "smell for solvent"). |
| D-016 | 11-02 | **Hazards and tools are watched live, but the alert is advisory** | At about 1 fps with 2 to 3 s latency, hand-near-hazard is a coaching cue, not a safety interlock. The docs and UI never present it as a guard. |
| D-017 | 11-02 | **Untrackable phrases are marked, not hidden** | SAM read a drawn saw blade as "gear". A hazard SAM can't find must show as "not trackable" on the dashboard, never be silently unwatched. It also costs no SAM call per frame. |
| D-018 | 11-02 | **Black frames are never sent** | A muted iOS camera still delivers frames, all black. They produced a procedure about "a black screen" and wasted SAM calls. |
| D-019 | 11-03 | **The mic proves itself: worklet, then ScriptProcessor, then backup recording** | On the user's iPhone the AudioWorklet path delivered nothing, silently. A running AudioContext is not proof of audio; the first chunk is. |
| D-020 | 11-03 | **Phones report telemetry to the server** | Field glitches were invisible. Two silent failures (0 audio bytes, 0 frames) were only found by reading server counters. Untrusted input is escaped, capped and rate-limited (security review). |
| D-021 | 11-03 | **Docs live in the repo and are updated in the same commit as the code** | The user's requirement: any developer or agent must be able to pick the project up cold. `AGENTS.md` is the entry point. |
| D-022 | 11-03 | **The expert's own keyframe is kept per step and shown to the judge** | It is few-shot recognition on the exact machine, under that light, and it costs no extra call. Measured: no added latency (6.9 vs 6.8 s). The same photo powers "Show me". |
| D-023 | 11-03 | **Ask Ustad answers by tool call, never prose: `answer`, `check_now`, `escalate`** | The answer becomes an action: point SAM at a part, show the expert's photo, run a check, call a supervisor. An answer can never mark a step done; `check_now` goes through the normal judge and the safety gate. Questions about skipping or bypassing safety must escalate. |
| D-024 | 11-03 | **Ask runs at `minimal` effort** | Measured on real photos: 3.3 s vs 5.8 s at `low`, the same tool chosen 3/3. Waiting is the worst part of asking for help, and the safety rules above don't depend on reasoning depth. |
| D-025 | 11-03 | **Questions are detected narrowly; the Ask button widens it for 12 s** | Each answer is a model call that talks over the worker. Chatter to a colleague must not trigger it. Rate limit: 8 a minute, one at a time. |
| D-026 | 11-03 | **Answers and pointers are spoken "asides"** | Found in a browser test: an answer replaced the step instruction on screen. The worker must always see what to do. |
| D-027 | 11-03 | **A capture take outlives its socket (in memory, 20 min TTL)** | Factory Wi-Fi drops. The phone keeps recording and syncs with job-clock times; the server rebuilds the timeline in place. Not persisted to disk: a server restart loses an unfinished take (stated in STATUS). |
| D-028 | 11-03 | **Procedure build runs as its own task; its result is kept for a rejoin** | A build takes 30 s or more. Inline, a drop lost the procedure, and pings went unanswered, so liveness killed the socket. |
| D-029 | 11-03 | **One socket at a time: `retire()` the old one; replies go to the socket they arrived on** | Found in a browser test: the `online` event and the backoff timer both connected, and the sync wrote to a socket still connecting, losing the offline frames. |
| D-030 | 11-03 | **Liveness by app-level ping (7 s) and silence (20 s)** | Phones leaving Wi-Fi leave sockets half-open with no close event. The server answers `pong`, including while it builds. |
| D-031 | 11-03 | **Self-improvement edits steps in place only, never adds or removes steps, and can only add to safety content** | Step numbers stay aligned with run history and insights. A model must never weaken a hazard, a reading range or a timer. Every edit needs approval, and every new phrase is SAM-checked first. |
| D-033 | 11-03 | **Changing a procedure needs a supervisor token** (`X-Supervisor-Token`; `SUPERVISOR_TOKEN` in .env, else a generated `data/supervisor_token.txt`, created owner-only (0600) in one step, gitignored and never logged). Improve is also rate-limited, 6 per 10 min | Security review: the demo link is public, so anyone with it could rewrite procedures or burn credit. A header, not a cookie, so cross-site requests can't carry it. Reading stays open for the demo. |
| D-034 | 11-03 | **Worker words reach the improve prompt quoted; code refuses edits that drop safety wording** | Security review: a worker could say "set step 2 to open the guard" and a question flows into the prompt. Quoted as data, and any instruction, criteria or mistake edit that loses a safety word (lock, isolate, guard, pressure, wait, never...) is discarded before a supervisor sees it. Errs toward dropping a good edit. |
| D-035 | 11-03 | **Capture memory is bounded**: 12 takes, 400 keyframes and 10 min of offline audio per take, size checked before decoding | Security review: `audio_gap` was capped per message, not per take, and takes were unbounded. A new recording evicts the longest-detached take. |
| D-036 | 11-03 | **A waiting take is never evicted for another client** (refines D-035): max 4 takes per client address (`CF-Connecting-IP` behind the tunnel), and only a client's own oldest detached take can give way. When full, new takes are refused | Security review: evicting the longest-detached take let anyone with the link open a dozen sockets and destroy an expert's offline recording. Refusing costs a retry; evicting costs the job. Caveat: on the LAN (not via the tunnel) the header could be spoofed, so per-client limits are best-effort there. |
| D-037 | 11-03 | **Client identity: `CF-Connecting-IP` trusted only from loopback; new takes rate-limited per client (6 per 10 min); near-empty abandoned takes (under 5 frames) expire after 2 min, not 20** (refines D-036) | Security review: the header could be spoofed by a LAN client to look like many clients and hold every slot. Cloudflare overwrites the header, so via the tunnel it is real; directly, the socket address is used. Short TTL for junk takes means held slots free quickly without ever evicting a real waiting recording. |
| D-038 | 11-03 | **Writer at `low` effort; phrase repair at `minimal`** | Measured on the user's real take: writer default 19.9 s, low 10.2 s (same steps), minimal 11.2 s. Repair call: low about 6 s, minimal 2.5 s, same top suggestion. |
| D-039 | 11-03 | **Repair asks only for alternatives to the phrases SAM missed, and tests them all with SAM at once** (supersedes the full regeneration in D-004's repair) | The full regeneration resent every image and took 60 s of an 87 s build on an 11 s take, doubling tokens. Now one small call plus parallel SAM: about 5 to 10 s, and it can't break steps that were already fine. |
| D-040 | 11-03 | **Long recordings are written in parts while recording, then merged with one text-only call** | One call with every frame of a 2 hour job is impossible (context, latency, cost). Parts of about 4 min (cut at the end of an utterance) are drafted in the background with at most 8 frames each, so tokens grow linearly and at stop only the last part, a merge and the check remain (measured: 9.2 s at stop for 3 parts). Parts own frames by index, narration by time. |
| D-041 | 11-03 | **A take's frames live on disk (`data/takes/<id>/`), deleted once the procedure is saved; capture sends a frame only when the view changed (or every 10 s)** | Memory must not grow with recording length. Change-gating cuts frames when hands rest without losing the end state (stop and marks force a frame). Raw audio is kept only as a fallback until live transcription works, capped at 20 min. Recording limit raised from 10 min to 2 h. Disk is bounded (security review): frames are size-checked before decoding (700 KB encoded), must be JPEG, 300 MB per take and 1.5 GB across takes. |
| D-042 | 11-03 | **The build reports progress every 5 s; the phone reconnects on `visibilitychange`; the capture socket only gives up if the take never got an id** | Field bug 2026-11-03 13:49: the socket dropped 24 s into the build and the phone never reconnected, because the close handler treated "not recording" as "never started". The screen sat on "Building…" though the procedure was saved. |
| D-043 | 11-04 | **Background judges are pipelined**: up to 3 in flight, one every 1 s, each on a view not yet judged, and only while SAM sees the part; first look 2 s into a step (supersedes D-009's one judge every 5 s) | A judge call is ~4.5 s whatever the effort or image size (measured on the user's job). Waiting 5 s between looks and running one at a time made "done" to "advance" 13 to 30 s. Looks without the part in view could only ask for a better view, so they are skipped. |
| D-044 | 11-04 | **One look at confidence ≥ 0.9, with SAM seeing the part, advances an ordinary visual step; lockout, reading, timed and confirm steps still need two agreeing looks** (refines D-010) | The second look cost a whole extra judge call per step. A "done" tap has always been one look. The safety-gated steps keep the stricter rule. Two-look confirmation now accepts different frames in any order, and a stale "not yet" from an older frame can't cancel a newer pass. Measured, same real job: about 7 s per step (5.8 to 12.3) vs 11.5 to 30 s. |
| D-045 | 11-04 | **"Done" tap judged at `minimal`** (supersedes D-011's `low`) | On the user's real photos: minimal 4.5 s median 6/6, low 5.5 s 6/6, and an 11 s tail live. Smaller images (448 px) did not help. |
| D-046 | 11-04 | **A pass is spoken as "Done." then the next instruction; "what do I do / help / what now" is answered instantly from the step** (instruction, the expert's words, their photo, the live highlight), with no model call | The model's confirmation sentence cost ~3 s of listening per step, and a model answer to "what do I do" ~4 s for information already in the step. Corrections and specific questions still use the model. Speech rate 1.08. |
| D-047 | 11-04 | **Hindi changes the words, never the checks.** SAM phrases and success criteria stay as captured; `point_at` is always English; a translated field whose numbers differ from the source is discarded; a lost warning falls back to the original | SAM phrases are proven on the expert's footage in the language SAM reads. A wrong number in a work instruction is a safety problem, so it is checked in code rather than trusted to the model. |
| D-048 | 11-04 | **The Hindi judge writes only "ठीक है" on a pass** | A pass is spoken as "हो गया।", so the model's sentence was thrown away while costing time: median 5.1 s, then 4.1 s (English 3.3 to 4.0 s). Small samples, 6 each. |
| D-049 | 11-04 | **Trial sites are named on the landing page; the market line is India** (replaces "never named") | The user's decision: a textile clothing factory and MCPL (Modern Colours Private Limited), Ludhiana. A global hackathon, so no state or region in the pitch. |
| D-050 | 11-04 | **The public link runs on Modal, not Vercel** | Ustad holds WebSockets open and keeps state in memory and SQLite, which serverless functions can't do. One always-on container keeps a take and its socket together. |
| D-051 | 11-04 | **Data lives on the container's disk, backed up to a Volume every 30 s** | Modal Volumes aren't meant for a live SQLite file. A consistent copy (SQLite's backup API) is restored at start: a restart loses at most 30 s. Tested with a real redeploy. |
| D-052 | 11-04 | **The cloud copy starts clean** (3 procedures, real runs only), from a copy of the database | Judges shouldn't see test clutter, and the laptop's data is never touched. |
| D-053 | 11-04 | **Muse Glimmer gives a second opinion after the job; it does not guide live** | 8/8 right with no false passes, but 63 s median on NVIDIA's free API against 4.6 s for Muse Spark: a worker can't wait a minute per step, while an audit can. Keeps the live demo safe. |
| D-054 | 11-04 | **A second opinion never falls back to another model, and doesn't change the job's record** | The result names the model that judged, so a failed call must say so. It is a separate table: the original verdict stays what the worker was told. |
| D-055 | 11-04 | **It needs the supervisor token and warns before sending photos to NVIDIA** | NVIDIA's trial API asks for no confidential data or faces, and the link is public. Factory footage stays off it unless a person chooses otherwise. |
| D-064 | 11-04 | **Replays keep their video times and boxes in a sidecar table, `replay_checkpoints`** | `step_events` has no video time and `guide.record` drops boxes on a retry, which is exactly when an honest overlay still has to show what SAM saw. Changing `record` would touch live behaviour; a sidecar can't. |
| D-065 | 11-04 | **A replay's outcome is `replay: N of M verified`, never `completed`, and a failed SAM call is reported as an error, not a miss** | Nobody did this job, so the record must not read as if a person had. `guide.ground` turns an error into "no match", right for a live worker and wrong for a measurement, so replay watches for that log line. Replay also refuses a non-hosted backend, because factory footage goes only to Meta. |
| D-066 | 11-04 | **Replay does not upscale by default** | Measured on 5 frames and 5 phrases: found 9 of 25 native, 10 of 25 at 2x; best boxes agree (IoU 0.97 to 0.99) and scores are often identical to 7 digits. The one gain was the emergency stop at 30 s; the cost was 2 extra false boxes at 22 s. |
| D-067 | 11-04 | **The overlay draws only the highest-confidence box for a phrase** | The rule the app's own live view uses (`LiveBox.loop`). "blue plastic part" returns 11 to 15 boxes, some confidently on the blue control panel; drawing them all would be false. |
| D-068 | 11-04 | **The demo is the real app in Chromium, with the footage as a fake camera and speech as a fake mic** | The user asked for the exact UI and spoken instructions. It runs real ASR, the real writer, the real self-check and the real guide, so what is on screen really happened. Speech can't reach a recording from headless Chromium, so the app's own words are voiced afterwards, placed with the queue rules of `app.js`. |
| D-069 | 11-04 | **The demo's second server keeps its own takes folder** | A server start runs `clear_take_files()`, and the worktree's `data` is shared, so a plain second server would delete a take in progress on port 8800. |
| D-070 | 11-04 | **The demo's error moment comes from our own test run, labelled "From our own test run"** | The factory guide run flagged nothing, and a staged error would be false. The test run really failed twice and then passed, so its saved photos and reasons are shown as recorded. Photos are cropped only to leave out a branded bottle. |
| D-071 | 11-04 | **The demo reads what it shows from the source, and refuses a mismatch** | RL counts come from `episodes_report.json` and the build fails if the spoken total differs. Attempts and the stored second opinion come from the database. So a changed number can't quietly stay wrong in the cut. |
| D-072 | 11-04 | **The demo closes on the landing Proof section, not the public dashboard** | An editing choice about the closing shot only: the measured table and MCPL photos match the closing lines. The hand warning and step 4 frames in part 1 stay as recorded. |
| D-032 | 11-03 | **Metrics count only judged checks** | Questions, skips and notices are events, not checks; counting them skewed the pass rate. |
| D-056 | 11-04 | **A second opinion sends only the job's photos, never the expert's reference photo** | The supervisor agreed to send what the page shows. It also matches how Glimmer was measured. Live judging keeps the reference photo. |
| D-057 | 11-04 | **A fine-tune episode's label comes from what the frame shows, not from "different step means error"** | The machine is in view all the time: the emergency stop passes in every frame, so a blind rule would teach false alarms. Each frame+step is hold, fail, weak or unclear; unclear is never used, and step 0 is never a mismatch. Step 1 with no hand is tagged weak: it fails as written, but the worker may have seated the part and let go. A crop that hides a hand never turns "hands clear" into a pass. |
| D-058 | 11-04 | **Episodes are tool-call rows, not JSON in the reply text** | Production calls the open backend with tools and `tool_choice=required`. A model taught to write JSON as prose would produce no tool call, and `judge_step` reads that as "need a better view". The cookbook's `upload` check refuses rows with empty reply text, so these upload through the datasets API instead. Untested until a key exists. |
| D-059 | 11-04 | **Eval runs log to a separate database, `data/factory/rl/rl_eval.db`** | `/api/metrics` counts every row in `step_events`, so hundreds of eval rows would swamp the real numbers. Same schema, set by `DB_PATH` for the eval process only. SAM calls still go through the main database, so the budget guard counts them. |
| D-060 | 11-04 | **Live guiding stays on Muse Spark + SAM for this submission; a fine-tuned Glimmer would only ever review finished jobs, through its own settings** | The user's call. `REASONING_BACKEND` stays `hosted`. Pointing the shared `.env` at another model would also change the running server and break the NVIDIA second opinion. |
| D-061 | 11-04 | **No hosted-to-Glimmer failover in live guiding** | A 63 s median on a safety check is unacceptable live, and it would add a new path to the live product hours before the deadline. |
| D-062 | 11-04 | **The edge-case review checks a doubtful step's last saved photo, and counts the steps it can't check** | Only pass and fail save a photo, so a step that only ever got "can't tell" has none: the page says how many. A step that passed after a retry is doubtful, and its passing photo gets the second look. Low confidence means under `DOUBT_CONFIDENCE` = 0.8, a starting value that has not been tuned. A flagged error has no confidence field, but fail is already doubtful. |
| D-063 | 11-04 | **RL stops at a built pipeline; nothing was trained for this submission** | Fireworks needed credit or a card to make an API key, the user has no card, and chose to skip paid training. The 96 weak `flag_error` labels stay in the episodes, tagged, so any later result can be reported with and without them. Nothing may be called fine-tuned or RL-trained. |
| D-073 | 11-05 | **The public demo has a sign-in, and the landing page stays open** | Jobs, photos and spend were readable by anyone with the link. One shared code is honest for a demo; a plant would use its own single sign-on, per person. Attempts are limited, the cookie is signed and HttpOnly. |
| D-074 | 11-05 | **Spending limits are enforced before every paid call** | The old guard only stopped live watching. A public link needs a hard stop: total budget and hourly cap (`spend_stop`), plus limits on sessions per device, live sessions at once and session length. Set only on the public link through `MODAL_*` in `.env`. |
| D-075 | 11-05 | **The landing figure is a labelled concept view through glasses** | Nobody understood the old gauge drawing. It shows the real factory clip with Ustad's step, box, verdict and safety warning. Glasses with no display would speak the same words, and none of this has been tested on glasses, so the page says so. |
| D-076 | 11-05 | **All rights reserved, not MIT** | The Official Rules leave ownership with the entrant and don't require an open licence; the user doesn't want the project copied. Going from closed to open later is possible; taking back an open licence isn't. Organisers still get the licence the rules grant them. |
| D-077 | 11-05 | **The textile trial site is named: PI Cottex Pvt Ltd, Ludhiana** (adds to D-049) | The user's decision, with their photo and an on-ground clip from MCPL. Each tile in the gallery carries its site's name so nothing is attributed to the wrong factory. The market line stays India. |
